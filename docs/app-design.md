# App design

Run My AI is a Flutter desktop app for Linux and Windows; a macOS runner exists in `macos/`. It is a chat window with a model store, a settings page and a sidebar of saved chats. It uses `flutter_riverpod` for state, `sqlite3` for chats and `window_manager` for the window. Build and run commands are in `building.md`. Paths below are relative to the app folder.

## 2. State

`Storage`, `ChatStore` and `Backend` are plain objects exposed by `storageProvider`, `chatStoreProvider` and `backendProvider` in `lib/state/providers.dart`. They throw until `appWith` overrides them in the `ProviderScope`, so `main()` and every test choose their own. The notifiers below reach them with `ref.read`.

| Provider | Holds | Saved to |
|---|---|---|
| `chatsProvider` (`ChatsNotifier`, `ChatsState`) | The chat list (`ChatInfo`, no messages), pinned ids, the open chat with the messages shown (one path through its versions), the id of the chat being replied to, the message being edited (`Editing`), the shown `ChatKind`. | `chats.db` |
| `sectionProvider` | The `Section`: chat, code, store or settings. Choosing chat or code switches `ChatsNotifier` to that kind's chats. | not saved |
| `libraryProvider`, `pickedModelProvider` | Downloaded file ids, downloads in progress, the picked file; the picked `CatalogEntry`. | `library.json` |
| `catalogProvider`, `catalogFilesProvider` | The catalog from `Backend.loadCatalog`, and its files by id. | not saved |
| `prefsProvider` | Theme, sidebar hidden, text size, bell, own sound. | `settings.json` |
| `draftsProvider` | Unsent text per chat and per section's new chat. | `drafts.json`, 500 ms after typing stops |
| `foldsProvider` | Folded groups of the chat list, per section. | `folds.json` |
| `searchProvider`, `searchResultsProvider`, `findProvider` | The search box; its results (searched on the chat store's worker, the newest search wins); the chat opened from a result, with its highlights. | not saved |
| `archiveViewProvider` | The sections whose sidebar shows Archived. | not saved |
| `motionProvider` | `Motion`: how a reply moves while it is written (`smoothMotion` or `rawMotion`). | not saved |
| `thinkingProvider`, `thinkingClockProvider` | Per message (chat id and place): when its model started to think, and whether the user opened its thinking block. The clock is replaceable for tests. | not saved |
| `deleteGuardProvider` | `DeleteGuard`: when deleting a chat asks first. | not saved |
| `benchmarkProvider` (`BenchmarkNotifier`, `BenchmarkState`), `engineTabProvider` | The Benchmark tab's setup, the run going on (its series of readings, phase, disturbed reasons), the latest result and the history; which tab of the Engine page is shown. `hardwareMonitorProvider`, `promptCorpusProvider` and `runVersionsProvider` make what a run reads, so tests give their own. | `benchmark.json` (the setup), `chats.db` (the history) |
| `todayProvider` | Today's date, checked each minute, for the list headings. | not saved |
| `systemLightProvider` | Whether the computer is explicitly set to light. | not saved |
| `chimeProvider` | `Chime`, the reply-finished sound. | not saved |
| `windowMaximizedProvider`, `windowFocusedProvider`, `windowFullScreenProvider` | The window's state, from `window_manager` listeners. | not saved |

`ChatsNotifier` is the centre. It keeps messages in memory only for the open chat and the chat being replied to (`_replying`), writes every change to `ChatStore`, remembers each section's open chat (`_openIn`) and each chat's branch ids (`_branches`, section 4). Providers follow each other with `ref.listen`: `ChatsNotifier` follows `sectionProvider`, `DraftsNotifier` the chat list (a deleted chat loses its draft), `FoldsNotifier` `findProvider`, `SearchResultsNotifier` the search box and the chats, `Chime` the bell.

## 3. Data

`Storage.open()` uses the folder from `path_provider`'s `getApplicationSupportDirectory()`, or the folder named by the environment variable `RUNMYAI_DATA_DIR`. All saved data is in that folder:

| File | Form | Content |
|---|---|---|
| `chats.db` | SQLite | Chats, messages (a reply keeps its stats) and a word index; the benchmark history (section 10). |
| `settings.json` | JSON | `theme`, `sidebarHidden`, `textScale`, `bell`, `soundName`, `soundFile`. |
| `drafts.json` | JSON map | Draft key (a chat id, or `new:chat` / `new:code`) to text. |
| `window.json` | JSON | `width`, `height`, `x`, `y`, `maximized`. |
| `library.json` | JSON | `downloaded` (file ids) and `picked`. |
| `folds.json` | JSON map | Section name to folded group keys (`pinned`, or a day as `YYYY-MM-DD`). |
| `sounds/custom.<ext>` | audio | The copy of the sound file the user chose. |

`Storage` writes each JSON file to a `.tmp` file and renames it, and reads a missing or unreadable file as the defaults. `theme` holds `system` or the picked style (`light`, `silklight`, `dusk`, `dark`, `dark2`, `dark3`).json` keeps only ids.

`ChatDb` creates three tables: `chats` (id, number, title, created, updated, pin, kind, sort, archived, model, context, `sel`), `messages` (role, text, bookmark, thinking, thinking time, stopped, `parent`, `sel`, `conv`) and `messages_fts`, an FTS5 index that keeps no copy of the text. A message's row id is its chat's number shifted left 20 bits plus its own number in the chat (`ChatMessage.node`: the order the messages were made in), so a chat's messages are one range of ids and an index hit names its chat and message.

**A chat is a tree.** `parent` is the message a message follows (NULL: it starts the chat). A message with several followers has versions: an edited message is a new follower of the message before it, a reply written again a new follower of the message it answers, and each version keeps its own later messages. Nothing is deleted when a version is made. `sel` (on a message, and on the chat for its first messages) is the follower shown; NULL means the newest. `ChatDb.path` walks from the start taking the chosen follower at each place and returns the messages with `version` and `versions` (a message's place among its siblings, oldest first), the branch's `conv` and the number the chat's next message gets (`ChatPath`); saving a new message makes it the one shown at its place, so a chat reopens on the path it was left on. `select` (and `flip`, `pathTo`) set the chosen follower of a message and of every message before it. Search indexes every version, and a hit's message number names the message in whichever version holds it; `ChatsNotifier.openAt` makes that version the shown one. `conv` is the conversation id the engine keeps the message's state under: NULL for the chat's own id (every message made before the first new version), the branch's id for the messages of a branch. Schema changes are numbered upgrades on the database's `userVersion` in `_setUp`; version 12 added the tree, with each message of a saved chat following the one before it, so existing chats are one path and nothing is rewritten. Version 13 added `messages.stats` (a reply's stats as one JSON text; a message saved again without stats keeps the ones it has, so a reply saved as it grows does not lose them) and nothing else: older databases open with every message as it was. Chats saved by older versions as `chats/<id>.json` plus `pins.json` are moved in when the database opens.

`ChatStore` runs `ChatDb` on its own isolate. Saves (`createChat`, `addMessage`, `rename`, `setPins` ...) are sent without waiting and run in order; `addMessage` takes the message's number and its parent, and a message already saved under that number gets the new text. `path` (and `messages`, its list), `flip`, `pathTo`, `search`, `fillLines`, `flush` and `close` wait for an answer. When the store opens it also hands over every chat's branch ids (`branches`). The classes in `models.dart` are `ChatInfo` (a list row), `Chat` (with messages), `ChatMessage` (role, text, bookmark, thinking, stopped), `ChatKind` (chat or code), `CatalogModel` and `ModelFile`.

## 4. The chat flow

1. `_MessageBox` in `lib/ui/pages/chat_page.dart` owns the text field. Each change goes to `DraftsNotifier.set` under `draftKey(openId, kind)`. Enter calls `_send`; Shift+Enter starts a new line.
2. `_send` does nothing when no model is picked (`pickedModelProvider` is null), a reply is being written, a benchmark is running, or the text is blank. While another chat is replying or a benchmark runs the Send button is disabled and its tooltip says why. `ChatsNotifier.send`, `retry` and `sendQueued` also refuse while a benchmark runs, so nothing starts or swaps the engine under it. Otherwise it clears the box and calls `ChatsNotifier.send(text, model.file)`.
3. `send` makes a `Chat` if none is open (id from the clock, title from the first line cut at 40 characters), calls `ChatStore.createChat` or `setUpdated`, and saves the user message with `ChatStore.addMessage`. It adds an empty assistant `ChatMessage` to the chat in memory and sets `replyingId`.
4. It calls `reply(chatId:, model:, messages:)` on `backendProvider`. That returns a `Stream<String>` of pieces. Each piece goes to `_appendToReply`, an error to `_finish()`, the end to `_finish(finished: true)`.
5. `_appendToReply` grows the last message of `_replying` and, if that chat is open, publishes it as `ChatsState.open`. `ChatPage` watches `open` and builds each message as `_Message` inside `_MessageWithActions`. The last assistant message is a `LiveReply` (`lib/ui/live_reply.dart`), which spreads the pieces evenly and paints them in behind a moving edge as `Motion` says. `ReplyFollower` (`lib/ui/follow.dart`) keeps the page at the end while the user is at the bottom.
6. While a reply grows it is saved with `ChatStore.addMessage` about once a second (marked stopped until it ends), and `_finish` saves it as it is. A reply stopped or failed before its first piece is dropped, unless it has thinking: then it stays with its thought, marked stopped, and the page shows a small "Stopped" note where the answer would be. Such a reply is left out of what the model is sent. A reply that ended by itself calls `Chime.replyDone`, which plays the sound 350 ms later if the bell is on. The Stop button and Esc call `ChatsNotifier.stop`, which cancels the subscription and calls `_finish()` with no sound.

A reply that thinks shows its thought in a `ThinkingBlock` (`lib/ui/thinking_block.dart`): one header row, "Thinking… 12 s" and then "Thought for 12 s" (the same `thoughtLength` rounding in both), that a click opens or closes at any moment. It starts closed; while the model thinks the header pulses and a line under it shows the latest line of the thought. Open, the thought streams in a window that follows its end unless the user scrolled up. `ChatsNotifier` starts the message's clock in `thinkingProvider` at the first piece of thought and reads the saved duration from it; the block reads the clock and the open state from there too, so scrolling away or leaving the chat resets nothing. Blocks are forgotten with their messages (a deleted chat, a reply written again).

Opening another chat does not stop the reply: `_replying` keeps it, and the message box of other chats shows a hint until it ends. One reply runs at a time.

### Versions, editing and writing a reply again

`ChatsState.open` holds one path through the chat's versions. Under each message, `_MessageWithActions` shows `‹ 1/2 ›` when the message has more than one version (always, also while a reply is being written) and its buttons: Copy, Edit (a sent message), Regenerate (a reply), Bookmark. They show under the pointer, and always under the chat's latest reply. Edit and Regenerate are disabled, with the tooltip of the Send button (`_sendBlock`: "A benchmark is running." or "... is generating a response. Stop it to send."), while any reply or a benchmark runs; Copy stays enabled. `ChatsNotifier.flip(index, step)` asks `ChatStore.flip` for the neighbouring version, which shows it and everything after it as last chosen there; the thinking blocks and the speed line are tied to a message's number, so each version has its own.

**Flipping while a reply is written.** The arrows stay enabled in every message of the chat, the reply's own included; Edit, Regenerate and Send stay disabled, and Stop stops the reply wherever the user is looking. Flipping only changes what `ChatsState.open` shows: the reply keeps growing in `_replying` (the notifier's own copy), is saved as usual, and is put into `open` only while the version on screen is its own (`_away` says it is not). So that a flip can go to it or from it, `flip` first saves the reply as it is (even empty, as one that did not get to its end; one that ends empty is taken out of the database again), and a path read from the database gets the reply's in-memory copy in place of its saved one (`_pathChat`). `ChatsState.replyingPath` (the number and version of each message of the reply's path) lets the page tell which version is being written whichever version is shown: only the reply on screen has the speed line, the loading line and the thinking clock, and `writingLabel` puts a small "writing" beside the arrows of the reply itself, and "2 writing" beside those of the place where another version is shown, naming the one to flip to. When the reply ends the view stays where the user left it (a reply that fails is shown, for its Try again); the chat's saved version is the one the user flipped to, and a chat left and opened again shows that one while the reply goes on.

- **Edit.** `beginEdit(index)` (a sent message, no reply or benchmark running) puts `Editing` (chat, message number, a new branch id) in the state and the message's text in `editText`; `_MessageBox` loads it into the box, shows "Editing message · Cancel" above it, and does not keep what is typed as the draft, so Cancel (or Esc) brings the draft back. The message's bubble is outlined. `sendEdit` posts the text as a new version of the message, after the messages before it, with a reply in the new branch; what came after the old version stays with it. Opening another chat, a new chat, another section's chat or flipping a version cancels the edit.
- **Regenerate.** `regenerate(index)` writes the reply again from the messages before it, as a new version in a new branch (on an older reply too: the later messages stay with the old version). The new reply is saved with its first words; one stopped before any is dropped, the version shown before comes back and the branch's state is erased.
- **Branches and engine states.** The engine keeps a saved state per `X-Conversation-Id`. The original path uses the chat's id; each new version starts a branch with its own id (`<chat id>-b<time>`), kept in `ChatMessage.conv` and used for the rest of that branch (`Chat.conversationId` is the last message's). `_startBranch` notes the id and, with a backend that is a `BranchControl`, calls `forkBeforeFirstUse(from, to)`, where `from` is the conversation of the path the version was made on; `EngineBackend` then calls `POST /cache-disk/fork` with `{"from", "to"}` once the engine is ready and before the first request, logs a failure and goes on (the engine reads the chat once), and gives the new conversation the oldest-messages cut (`_leftOut`) of the old one. A new version of the chat's first message copies nothing: nothing is shared. The pins list sent to the engine holds every branch id of each pinned chat (resent when a branch is made in a pinned chat); archiving and deleting a chat erase every branch id.
- **Starting early.** `beginEdit` on a message older than the latest exchange (not the first message) asks `BranchControl.readAhead`: if the engine is already running that chat's model with its command, it forks the state to the new branch's id and sends the messages before the edited one with `n_predict: 0`, `cache_prompt: true`, `cache_disk_save: false` and that id. It never starts or swaps the engine, and nothing happens while a reply or a benchmark runs. Send uses the same branch id (the request waits behind the read in the engine). Cancel calls `cancelReadAhead`: `DELETE /v1/stream?conv_id=...` and an erase of the id. The latest message and the latest reply need no early start: their state is saved.

## 5. Windows and platform code

- **Window.** `setUpWindow` (`lib/window/app_window.dart`) runs before `runApp`. It initialises `window_manager`, sets the minimum size (760 x 520), restores the saved size and place, holds back the window's own close (`setPreventClose`) and adds `_WindowSaver`, which writes `window.json` 500 ms after the window stops changing (while maximized it keeps the last normal size). A saved place is used only if the window's top row is still on a screen (`screen_retriever`), and never on Linux under Wayland. `CloseGuard` (`lib/ui/close_guard.dart`) closes the window instead: at once when nothing runs, else after asking "Close anyway?" while a reply or a benchmark runs; the reply so far is saved first, and the engine ends with the app.
- **No system title bar.** On Windows and macOS `setUpWindow` hides it with `setTitleBarStyle`; the macOS runner starts the window hidden and `setUpWindow` shows it. On Linux `linux/runner/my_application.cc` sets an empty GTK title bar (GTK keeps the shadow and resize edges), makes the window see-through on a composited screen and rounds it by 8 px.
- **The top row** is drawn by the app (`lib/ui/title_bar.dart`): `WindowDragArea` (drag, double-click to maximize, right-click for the window menu), `WindowButtons` (Windows and Linux), `WindowShape` and `WindowEdge` (the outline, and rounded corners on Linux), `TitleRowFade` (dimmed while the window is behind). `WindowLook` (mac, windows, linux) picks the style; `RUNMYAI_LOOK` previews another system's, and the mac look on another system gets Apple's buttons from `MacButtonsPreview`.
- **Computer theme.** `SystemLightNotifier` (`lib/system/appearance.dart`) reports whether the computer is explicitly set to light. On Linux it runs `gdbus` to read the freedesktop portal's `color-scheme` and falls back to Flutter's platform brightness; on Windows and macOS it uses Flutter's.
- **Native sound library.** `native/sound.c` is built as the shared library `runmyai_sound` by `linux/CMakeLists.txt` and `windows/CMakeLists.txt`. It exports `sound_check`, `sound_play`, `sound_playing` and `sound_stop`, plus `sound_check_w` and `sound_play_w` on Windows (UTF-16 paths). `SoundPlayer.load()` in `lib/system/chime.dart` opens it with `dart:ffi` from next to the executable: `runmyai_sound.dll` on Windows, `lib/librunmyai_sound.so` on Linux, `../Frameworks/librunmyai_sound.dylib` on macOS. If it cannot be opened, `load()` returns null and `Chime` plays nothing; `macos/` has no build rule for it. `Chime` plays the user's copy in `sounds/`, else the app's `reply-done.mp3` from `flutter_assets`, and polls `SoundPlayer.playing` every 250 ms to close the sound device. `Chime.choose` copies a file picked with `file_selector` into the data folder.
- **Platform folders and paths.** The data folder comes from `path_provider`. The sound library, the app's sound and the Linux window icon are found from `Platform.resolvedExecutable`. Shortcuts use Cmd on macOS and Ctrl elsewhere (`_cmd` in `lib/ui/shortcuts.dart`).

## 7. Conventions

- Files are `snake_case.dart`. In `lib/state/` a notifier, its state class and its provider sit together, the provider right after the notifier: `final xProvider = NotifierProvider<XNotifier, X>(XNotifier.new);`.
- State classes are immutable (`const` constructors, `final` fields). Those with several fields have `copyWith` (`Prefs`, `ChatsState`); where a field can be set to null it takes a closure (`openId: () => null`).
- Notifiers write to disk through `Storage` or `ChatStore`. Services come from the three providers in `providers.dart`, so tests swap them (`overrideWith`, `overrideWithValue`).
- Widgets that read state are `ConsumerWidget` or `ConsumerStatefulWidget`, watch with `ref.watch(provider.select(...))`, and are private (`_Name`) unless another file needs them.
- Screens read colours from `context.colors` (`AppColors`: `page`, `text`, `textSecondary`, `border`, `selected` ...). The theme sets no accent colour. `DarkLook` (flat, silk, slashes) sets the decoration a theme adds. Colour is for graphs and errors; everything else is grey. A new theme gives every role of `AppColors`, and `test/colors_test.dart` checks its contrast.
- **Buttons:** every button is one of four widgets in `lib/ui/buttons.dart`, all built on `Clicky.builder` (`lib/ui/clicky.dart`: hover, press with a 0.97 scale, Tab focus with a ring, Enter and Space, screen-reader semantics): `AppButton` (normal; `danger` writes the label in the danger colour), `MainButton` (the main action of a place: Start, Save; with `danger`, a delete question's button), `OptionPill` (one of a set, or a button that opens a list; `chosen` shows it on) and `AppIconButton` (`quiet`, `outlined` or `main` look; `round`, `chosen`). Their colours are the button, option, main, disabled and row roles of `AppColors`; borderless things (sidebar rows, the top row) use `rowHover`, `rowPressed` and `rowSelected`. A plain clickable area with no look of its own is a `Clicky` around its child. Do not use Material's `TextButton`, `OutlinedButton` or `FilledButton`.
- Widgets a test taps carry a `Key('...')` (`send`, `stop`, `store`, `bell`, `new-chat`, `theme-family`, `motion-smooth`; under a message `copy-N`, `edit-N`, `regenerate-N`, `version-prev-N`, `version-next-N`; `edit-cancel`).
- Benchmark widgets a test taps: `benchmark-start`, `benchmark-stop`, `benchmark-test-mode`, `benchmark-context-N`, `benchmark-prompt-ID`, `graph-row-ID`, `meter-SERIES`, `words-chart`, `fold-TITLE`, `compare-pick`, `history-ID`; under a reply `more-N` (its card).
- Classes and non-obvious fields carry a `///` comment in plain words about what they do.
- **A new setting:** add the field with a default to `PrefsData` in `lib/data/storage.dart` and to `readPrefs` / `writePrefs`; add it to `Prefs`, `copyWith`, `PrefsNotifier.build` and `_save` in `lib/state/prefs.dart`, with a notifier method; add the control to `lib/ui/pages/settings_page.dart` (`_Menu` and `_Choice` take an `id` that becomes the widget key); add a test.
- **A new screen:** add a value to `Section` in `lib/state/section.dart`, a page under `lib/ui/pages/`, and a case in the `switch` in `Shell.build` (it has no default, so the compiler finds a missing case); add a sidebar entry next to Store and Settings in `lib/ui/sidebar.dart`.
- **A new shortcut:** add the binding to the map in `_AppShortcutsState.build` (`lib/ui/shortcuts.dart`) and a row to `ShortcutsSheet._groups`.
- **A new backend call:** add it to `Backend`, implement it, and call it through `ref.read(backendProvider)`.

## 8. Auto commands

`lib/engine/auto_commands.dart` (`lingAuto`, `flintAuto`: one command per context length, 4k to 262k) is the Auto profile's flags. It is generated: never edit it. `tool/sync_auto_commands.sh` sources `presets/ling.sh` and `presets/flint.sh` (Flint with its default case), calls `preset_command <size>` for every size in the preset's `PRESET_SIZES`, and keeps what the app stores: the environment settings first (`GGML_CUDA_*=...`, kept as `EngineFlags.parse` reads them), then the flags. What the app supplies itself when it starts the engine is cut out: the `systemd-run` memory-cap wrapper (it must be the words `_memoryCap` in `engine_backend.dart` writes, else the script stops), the program, `-m` and the model file, `--host` and `--port`. It also stops on anything the app refuses in a command (the flags `commands.dart` lists as supplied by the app, `LD_*`, `DYLD_*`, `PATH`), a quote, `$` or `\` in a flag, or a path into the presets' folder left over. Run it from anywhere after a preset changes: `runmyai/tool/sync_auto_commands.sh`. `--check [FILE]` writes nothing and exits 1, showing the difference, when the file is not what the presets give; `test/auto_commands_test.dart` runs it. Today every flag of both presets can be stored; Flint's other machine cases (`FLINT_CASE=2`, `3`) are not generated: the app has one Auto command per context length.

## 9. About

- **Versions.** The app's (`appVersion` in `lib/state/about.dart`, kept equal to pubspec.yaml by a test) and the engine's (`engineVersionProvider`): first what `llama-server --version` in the engine folder prints (`readEngineVersion`, 5 s at most), else what the running engine reports (`EngineControl.reportedVersion`, the `build_info` of its `/props`), else "unknown".
- **Credits.** The makers, the engine's base (llama.cpp and ggml, with parts from ik_llama.cpp) and the thanks list (`thanksProjects`, `thanksPeople`), the same names as the "Thanks" section of the engine's README (a test compares them).
- **Licences.** The app's own, the engine's (which carries the ggml authors' notice) and ik_llama.cpp's, from `assets/licenses/` (copies of `LICENSE`, `llama.cpp/LICENSE` and `llama.cpp/licenses/LICENSE-ik_llama.cpp`; a test compares them, so copy them again when a source changes), and the Flutter framework's and packages' licences, read from `LicenseRegistry` (one row per package). ## 10. The Benchmark tab

The Engine page's second tab (`lib/ui/pages/benchmark_tab.dart`, a part of `engine_page.dart`) is one page from top to bottom: **Settings**, **Live**, **Full result** (only after a run) and **History**. Detail stays behind a click (`Fold`, an opened graph row).

**Settings.** The profile (Auto, the user's own, or Test mode, whose flags are edited here, never saved to a profile and kept for next time), the context length of that profile, the prompt, the longest reply, the two warm-up messages, thinking (shown, and recorded), the note "For accurate results, close other apps first", and Start / Stop. Start is greyed while a chat replies or the settings cannot run (`BenchmarkNotifier.problem`: a bad command, no own text, a prompt that does not fit). The prompts are the story chat (default) and about 1k, 4k, 16k and 32k tokens of varied real text, or the user's own. A size is greyed when `promptFits` says it and the longest reply do not fit the context (the engine's own room rule, `ContextFit.replyRoom`). The long text is made by `PromptCorpus` (`lib/benchmark/prompts.dart`): one passage in turn from each text of `assets/benchmark/` and the story, each passage once, never repeated; `fitPrompt` counts it with the running engine's `/tokenize` (`EngineInsight.countTokens`) and cuts it to within 2 % of the size.

**A run** (`BenchmarkNotifier.start`): the readings of the machine begin, the engine is stopped and started fresh with the profile's command and memory cap (the flag `--moe-stream-timing 1` is added only when the engine's `--help` lists it, `EngineInsight.acceptsFlag`, and the user's flags do not set it; the record names what was added), the warm-up messages and then the measured message go in one conversation, each reply stopping when the model stops (the longest reply is only `max_tokens`). Requests carry `cache_disk_save: false` and `return_progress` (`EngineRun.forBenchmark`). The conversation's state is erased and the engine is stopped afterwards. Stop keeps nothing.

**Readings** (`lib/benchmark/hardware.dart`). `HardwareMonitor` runs `SystemReader` on its own isolate, twice a second, and sends one `SystemSample` (a map of series ids to numbers) each time. A value the machine does not give is left out. The ids: `cpu.load`, `cpu.other` (the CPU other programs than the engine used: everything busy less the engine's own jiffies), `cpu.core.N.load/mhz/mhzMax`, `cpu.mhz`, `cpu.power`, `cpu.temp`; `ram.total/used/engine/other/cache/available/swap/swapTotal/swapActivity`; `ssd.read/readMax` (the NVMe link's speed)`/iops/queue/busy/temp`; `sys.battery`; per card `gpu.N.load/power/powerLimit/powerMax/clock/clockMax/temp/tempMax/vram/vramTotal/pcieTx/pcieRx/pcieMax/reasons`. NVIDIA cards come through `libnvidia-ml` opened at run time with `dart:ffi` (`nvml.dart`; nothing is spawned, and a missing library means no readings from it); AMD cards (discrete and integrated) from `/sys/class/drm/card*/device` (`amd_gpu.dart`: `gpu_busy_percent`, `mem_info_vram_*`, `pp_dpm_sclk`, the hwmon power, power cap and temperature), named from the PCI id list. Every card is its own row, the AMD ones numbered after the NVIDIA ones. Reading /proc and /sys is Linux; on Windows only the NVIDIA library gives numbers, and the rest of the machine's rows say so.

**Series.** Each tick of the run (the machine's reading, the engine's latest numbers, the live speeds) is one entry in a `RunSeries` (`series.dart`): columns by id on one time axis, with the phases (Load, Warm-up, Prompt, Reply). The live view reads the same object each time it paints. A finished run keeps it shrunk to 200 ticks (neighbours averaged, the slowdown-reason flags kept), a constant column as one number.

**The engine's counters.** Once a second the run asks `GET /moe-stream/stats` (`EngineInsight.liveStats`). The document has `total` (since the model was loaded), `request`, and `layout`; each figure part has `prompt` and `reply` counters (`tokens`, `misses`, `stall_ms`, `expert_uses`, `ram_hit_percent`, `vram_hit_percent`, `mib_read`, `guesses.{issued,in_time,late,missed,wasted,cancelled}`), `vram.follow_swaps`, `per_layer` and, with `--moe-stream-timing`, `time_per_word`. `EngineSnapshot.parse` reads it leniently (other names and a flat document work too) and `EngineStatsTracker` turns two readings into SSD wait and reads per word, the RAM and VRAM hit shares, the guess shares and VRAM swaps. A missing route or a model that does not stream gives "not available" in the Engine row and nothing else changes. The result takes each layer's numbers and the parts of a word (SSD wait, CPU, hand-off, other; the GPU's kernels run beside them and are named, not added) from the final response's own `timings.moe_stream`, and falls back to the difference between two readings.

**Disturbed** (`disturbance.dart`), checked on every tick and shown live: on battery at any moment or at the start; other programs busy at the start (the CPU above 25 % or a card above 30 %); other programs' CPU use above 10 % on average or at 30 % for 6 seconds; a card held down while it works (load of at least 30 % in at least four ticks): its power limit set below 70 % of what it can be given, or far under its limit (below 60 %) while the driver reports a slowdown, or its clock under half of its highest. A card whose driver sets its clock by the load (AMD's) is not judged by clock. The reasons are in the result and in the history row.

**The result** (`result_view.dart`): the headline numbers; where the time per token went; every token as a clickable chart (a click puts the graphs' cursor at that token's moment, from the engine's per-token times in the final stream: `timings_per_token`); the spread with p50 / p90 / p99 and the slowest token; then, opened with a click, phases, streaming, memory layout (from the engine's `layout` where it gives it), each layer (heat map), the hardware over the run with the slowdown moments, the reply and why it ended, the setup record (flags, profile, model file size and date, engine and app versions, context, prompt, warm-ups, thinking, computer, power) and a comparison with any other run (headline deltas, the flags that differ in bold).

**History.** `BenchmarkResult` is one JSON text in the `benchmarks` table (`ChatDb.addBenchmark` returns its id); the newest `ChatDb.maxBenchmarks` (60) are kept. Rows from before the graphs open as they were (every new field is optional). A row opens to its full result with its graphs; it has Copy flags and Delete (a second click within four seconds).

## 11. The reply card

A "⋯" button after Copy and Bookmark under a reply opens a small card (`ReplyStatsCard`, `lib/ui/reply_card.dart`): generation speed, prompt processing, TTFT, tokens in and out, time, SSD wait (ms/token) and the share found in RAM, and the model, profile and context length that wrote it. `ChatStreamReader` takes each word's time from the running totals the engine sends with every message and the end of the stream gives `ReplyDone` the engine's timings, which `ReplyStats.fromTimings` turns into the numbers (a number the engine did not give is left out, and with no numbers there is no button). `ChatsNotifier` keeps the stats with the reply when it ends by itself and saves them with the message (`messages.stats`); a stopped reply has none.
